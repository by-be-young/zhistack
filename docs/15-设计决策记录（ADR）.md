# 15 · 设计决策记录（ADR）

每条记录：背景 → 决策 → 备选 → 后果。编号 ADR-001 起，后续变更新增而非改写。

---

## ADR-001 纯前端、无后端

**背景**：个人备考工具，单用户，数据敏感度低但隐私要求高；预算为零，需长期在线。

**决策**：不做后端，全部逻辑与数据在浏览器内闭环，GitHub Pages 托管静态产物。

**备选**：
- Supabase / Firebase：跨设备同步方便，但引入账号、网络依赖与免费额度限制。
- 自建 Nest + 服务器：可控性最高，运维成本与持续费用高。

**后果**：隐私零风险、部署零成本、离线可用；代价是无自动同步、内容更新需重新部署、无法做服务端推荐与排行榜。该代价在当前场景可接受。

## ADR-002 hash 路由而非 history 模式

**背景**：GitHub Pages 不支持 SPA 的 404 回退。

**决策**：使用 `createWebHashHistory`，URL 形如 `/#/practice/session/s-…`。

**备选**：history 模式 + `404.html` 重定向脚本（业界常用 hack）。

**后果**：刷新与直接访问永不 404，配置为零；代价是 URL 不够干净、SEO 不友好（本项目不需要 SEO）。

## ADR-003 存档放 localStorage，PDF 放 IndexedDB

**背景**：学习存档小（< 200 KB）、需同步读写；PDF 大（数十 MB）、只需按需读取。

**决策**：分而治之。存档单 key 整体读写；PDF 存 Blob。

**备选**：全部 IndexedDB（异步复杂）、全部 localStorage（容量不够）。

**后果**：存档读写简单、可原子替换、易导出；PDF 不拖慢主流程。风险是 localStorage 同步写入可能阻塞，已用防抖与体积上限控制。

---

## ADR-004 知识点与题目全静态打包

**背景**：内容需版本可控、构建期校验，运行时不编辑。

**决策**：内容以 JS 模块形式随构建打包，`validate-data` 在 prebuild 校验。

**备选**：运行时 fetch JSON（多一次请求、无类型校验）、CMS（引入后端）。

**后果**：首屏即可检索、无网络依赖、脏数据无法上线；代价是更新内容必须重新部署，且包体随内容增长。

---

## ADR-005 组卷以知识点为抽样单位

**背景**：纯随机抽题会让同一知识点重复出现，覆盖面差。

**决策**：先按知识点分桶，轮转取题，单知识点占比 ≤ 30%，再按难度配额。

**备选**：完全随机、按章节权重随机。

**后果**：一套卷覆盖更广、诊断更有意义；代价是实现稍复杂，且题池小时需要放宽规则（已在算法中定义降级顺序）。

---

## ADR-006 掌握度采用「平滑 + 置信度收缩」

**背景**：样本稀疏时，1 题答错会把掌握度打到很低，产生错误推荐。

**决策**：Laplace 平滑正确率，再用 `confidence = 0.4 + 0.6·min(1, a/6)` 把低样本结果向 55 分收缩。

**备选**：直接用正确率（稀疏时噪声大）、Elo/IRT（需要大量数据与校准）。

**后果**：新知识点不会因一次失误被判死刑，推荐更稳；代价是公式不直观，需在 UI 中用「四要素拆解」解释。

---

## ADR-007 抽卡保底采用「双计数 + 十连保底」

**背景**：纯概率抽卡在短期内可能出现连续 N 卡，挫败感强。

**决策**：SSR 90 抽硬保底；十连内前 9 抽无 R+ 则第 10 抽强制 R+。概率固定公示。

**备选**：纯概率（简单但体验差）、递增概率（实现复杂，公示困难）。

**后果**：最坏情况可预期，体验稳定；代价是需要维护两个计数并处理「同时触发」的优先级（SSR 优先）。

---

## ADR-008 错题用状态机而非布尔「已掌握」

**背景**：一次答对不等于掌握，需要观察窗口。

**决策**：`new → reviewing → mastered`，答对 2 次出本，答错回退；30 天内再错则回炉。

**备选**：答对一次即移除（过于乐观）、按 SM-2 排期（v1.0 过重）。

**后果**：出本更可信，错题本能真正变薄；代价是用户需多练一次，短期看「效率低」，长期正确率更高。

---

## ADR-009 视觉用原生 CSS 令牌，不引入 UI 框架

**背景**：需要独特视觉（工业薄雾 + 马卡龙），且控制包体。

**决策**：自建令牌与组件样式，深浅主题用 CSS 变量切换。

**备选**：Tailwind（原子类可定制，但产物与阅读成本）、Element Plus（风格冲突，体积大）。

**后果**：视觉完全可控、产物轻；代价是组件需自己写，一致性靠规范约束（04 文档）。

---

## ADR-010 统计以「会话 + 明细」为唯一事实源

**背景**：累计值（题量、正确率）若只存汇总，写入失败会造成长期漂移。

**决策**：保留 `sessions` 与 `knowledge` 明细，累计值可由明细重算；提供「重建统计」。

**备选**：只存汇总（体积小但不可修复）。

**后果**：数据可自愈、可审计；代价是存档稍大（已设 500 会话上限）。

---

## ADR-011 日期以 04:00 为分界

**背景**：备考常在深夜进行，0 点切日会把「同一晚的学习」拆成两天，打卡与任务统计失真。

**决策**：`dayKey` 以本地 04:00 为界；周以周一 04:00 起。

**备选**：自然日 0 点（标准但不符合学习作息）。

**后果**：更贴合实际作息，跨日任务不误重置；代价是需要在所有日期计算处统一调用 `core/time.js`，禁止各页面自行 `new Date()` 取日。

---

## ADR-012 内容与代码同仓

**背景**：内容需要版本追溯与构建校验。

**决策**：`src/data/*` 与代码同仓，`docs/` 同仓。

**备选**：独立内容仓（增加同步成本）。

**后果**：一次提交即可还原「某版本的完整站点」；代价是仓库体积随内容增长（当前可控）。
