# 12 · 部署与运维手册

## 1. 托管形态

| 项 | 值 |
| --- | --- |
| 仓库 | `https://github.com/by-be-young/kaoyan-408`（public） |
| 托管 | GitHub Pages（Actions 构建，非分支直发） |
| 地址 | `https://by-be-young.github.io/kaoyan-408/` |
| 基础路径 | `/kaoyan-408/`（Vite `base` 固定） |
| 构建产物 | `dist/`，纯静态 |
| 自定义域名 | 未启用（如需启用，见 §6） |

## 2. 工作流

`.github/workflows/deploy.yml`：

```yaml
name: 部署到 GitHub Pages
on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run build          # prebuild 内含 validate-data
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist }

  deploy:
    needs: build
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

## 3. 首次部署步骤

1. 仓库 Settings → Pages → **Build and deployment → Source: GitHub Actions**。
2. 推送 `main`，等待 `部署到 GitHub Pages` 工作流完成（约 1–2 分钟）。
3. 访问 `https://by-be-young.github.io/kaoyan-408/`，确认首页 200 且资源加载完整。
4. 若返回 404：检查 Pages Source 是否选对、工作流是否成功、`dist/index.html` 是否存在于 artifact。

## 4. 构建配置要点

| 配置 | 值 | 原因 |
| --- | --- | --- |
| `base` | `'/kaoyan-408/'` | 子路径部署，否则 JS/CSS 404 |
| 路由 | hash 模式 | Pages 无 SPA 回退，避免刷新 404 |
| 静态资源 | 带哈希文件名 | 长缓存安全 |
| `public/` | 仅 `favicon.svg`、`404.html`（可选） | 减少体积 |
| 环境 | 无 `.env`，无密钥 | 纯静态，无秘密可泄露 |

## 5. 发布流程（日常）

```
1. 本地改动 → npm run dev 自测
2. npm run build（validate-data 必须通过）
3. git add / commit（提交信息用中文，说明改了什么与为什么）
4. git push origin main
5. 等待 Actions 成功（约 1–2 分钟）
6. 打开线上 URL，验证首页 + 任一深层路由
7. 若失败：读 Actions 日志 → 修复 → 重新推送
```

提交信息格式：`<模块>: <动作> <对象>`，例 `练习: 修复多选漏选半分未生效`。

## 6. 自定义域名（可选）

1. DNS 添加 `CNAME`：`kaoyan.be-young.top` → `by-be-young.github.io`。
2. 仓库 Settings → Pages → Custom domain 填入域名，勾选 Enforce HTTPS。
3. `public/CNAME` 写入域名（否则每次部署会重置）。
4. 等待证书签发（数分钟至 24 小时）。

## 7. 回滚

| 方式 | 操作 | 影响 |
| --- | --- | --- |
| 代码回滚 | `git revert <commit>` → push | 触发重新部署，约 2 分钟 |
| 临时下线 | Settings → Pages → Unpublish | 站点 404，仓库保留 |
| 内容回滚 | 回退 `src/data/*` 并推送 | 已下架题的历史记录仍可复盘 |

注意：回滚代码不影响用户本地存档；但若回滚改变了 `schemaVersion`，旧存档可能触发迁移失败，需在发布说明中提示。

## 8. 缓存策略

- Pages 对 HTML 设置较短缓存（约 10 分钟），对带哈希的 JS/CSS 长缓存。
- 用户升级后若看到旧版：强制刷新（Ctrl+F5）或在 URL 后加 `?v=日期`。
- 更新发布后若页面表现异常，优先怀疑缓存，其次看 Actions 是否真的成功。

## 9. 监控与自检

无服务端监控。用以下轻量手段：

| 检查 | 频率 | 方法 |
| --- | --- | --- |
| 站点可达 | 每次发布 | `curl -I` 或浏览器打开 |
| 资源完整 | 每次发布 | 控制台无 404 |
| 数据校验 | 每次构建 | CI 日志中 `validate-data` 输出 |
| 存档健康 | 每月 | 设置页「存储占用」与「重建统计」 |

## 10. 故障排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 404 / 白屏 | `base` 配置错误或 Pages Source 非 Actions | 检查 `vite.config.js` 与仓库设置 |
| CSS/JS 404 | 资源路径未带 base | 确认 Vite 构建产物引用 `/kaoyan-408/assets/...` |
| 深层路由 404 | 使用了 history 模式 | 改回 hash 模式 |
| 页面空白但 200 | JS 运行时报错 | 看控制台；检查数据校验是否漏项 |
| 部署成功但显示旧版 | 缓存 | 强制刷新或加版本参数 |
| Actions 失败于 npm ci | lockfile 不一致 | 本地 `npm install` 更新 lock 后提交 |
| 用户反馈进度丢失 | 存档损坏 / 清缓存 | 引导从备份或导出文件恢复 |
| 抽卡概率异常 | 配置被改 | 对照 07 文档的概率表 |

## 11. 仓库维护约定

- `main` 为唯一发布分支，直接推送（个人项目，不设 PR 流程）。
- `docs/` 与代码同仓，文档变更随代码一起提交。
- `dist/` 不入库；`node_modules/` 不入库。
- 每季度检查依赖安全公告（`npm audit`），仅升级必要项，升级后完整回归一次。
- 站点为公开仓库，禁止提交任何个人隐私数据、token、本地 PDF。

## 12. 站点生命周期

| 场景 | 处理 |
| --- | --- |
| 内容长期不更新 | 保留站点，README 标注最后更新时间 |
| 需要迁移到自定义域名 | 见 §6，保留原 URL 可访问 |
| 需要下线 | Unpublish Pages，保留仓库与文档 |
| 需要多设备同步 | 不做云端；提供导出/导入，或后续接入可选后端（见 13） |
